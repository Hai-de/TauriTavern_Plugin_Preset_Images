# Preset Prompt Images 插件开发前背景信息

> 文档状态：开工前信息收集与方案对齐  
> 插件目标路径：`Plugin/Plugin_Preset_Images`  
> 参考样例：`Plugin/Plugin_Preset_Images/sample/空预设.json`  
> 最后更新：2026-09-30

---

## 0. 结论摘要

这个插件要解决的问题可以拆成四部分：

1. 在 Chat Completion 预设的“提示词条目”上增加图片附件。
2. 图片必须跟随预设 JSON 导入/导出，因此必须成为预设 JSON 的一部分。
3. 生成时，把条目上的图片转成 OpenAI-compatible Chat Completions 的 `content[].image_url` 消息内容部分。
4. 没有安装插件时，预设仍可被本项目/SillyTavern 正常导入并只以文本方式工作，不能因为多出的图片字段报错。

当前项目的关键事实：

- 预设由后端 `save_preset` / `file_preset_repository` 按普通 JSON `Value` 保存，没有额外 schema 校验。
- 前端预设对象包含 `prompts`、`prompt_order`、`extensions` 等字段；`extensions` 已经被上游和本项目用于扩展数据，例如 `extensions.tauritavern.omit_params`。
- PromptManager 目前只把 `prompt.content` 当作文本处理；生成消息时通过 `Message.fromPromptAsync()` 创建 `Message`，图片附件需要插件额外接入。
- `Message.addImage()` 已支持把图片追加为 `{ type: 'image_url', image_url: { url, detail } }`，并处理压缩和图片 token 估算。
- DeepSeek 原生/Rust 侧已经会保留 `image_url` 内容部分；但前端 `isImageInliningSupported()` 当前只把 `['deepseek-v4-flash-vision-exp', 'deepseek-flash']` 视为 DeepSeek 可视觉模型，未包含用户目标中的 `DeepSeek-V4.1-Flash`。
- 项目文档明确说明：Agent/headless 组装路径不会触发普通 `CHAT_COMPLETION_PROMPT_READY` 事件。因此若希望 Agent `preset.mode = ref` 也生效，插件不能只依赖该事件。

推荐的第一版边界：

- 数据存入 `extensions.tauritavern.presetPromptImages`，不改动 `prompts[]` 条目的标准字段。
- 只保证“相对位置（Relative）”提示词条目支持图片；绝对注入（In-chat）和附着到已有消息（Attach to existing message）作为后续扩展。
- 用 `PromptManager.prototype.preparePrompt` + `Message.fromPromptAsync` 的包装器把图片附加到最终消息。
- 对 `squash_system_messages` 和 system 角色图片做专门处理，避免 `content` 数组被字符串拼接破坏。
- 对图片做 MIME、大小、总预算和格式校验；图片嵌入预设 JSON 会显著放大 JSON。

## 1. 需求边界与成功标准

### 1.1 必须满足

- 插件位于 `Plugin/Plugin_Preset_Images`。
- 支持 Chat Completion Presets，即中文语境中的“预设”。
- 可以给预设里的提示词条目增加、查看、替换、删除图片。
- 预设导出为 JSON 时图片随 `extensions` 一起导出；导入预设后图片仍在。
- 没有插件时：
  - 预设 JSON 可以被正常导入；
  - 文本提示词、PromptManager、生成流程保持原行为；
  - 多出的插件字段不能被当成致命格式错误。
- 生成请求中的目标提示词消息变成 OpenAI-compatible 多模态内容，例如：

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "这是提示词文本" },
    {
      "type": "image_url",
      "image_url": {
        "url": "data:image/jpeg;base64,...",
        "detail": "auto"
      }
    }
  ]
}
```

- 第一个目标模型为 `DeepSeek-V4.1-Flash`。但当前项目中的确切模型 ID、接入来源和视觉能力还需要确认（见第 8 节）。

### 1.2 建议明确不做或暂缓

- 不修改上游 SD、TTS、视觉生成图片等无关链路。
- 第一版不处理 `request_images` / `request_image_*`，这些是“请求模型生成图片”的参数，不是“向提示词输入图片”。
- 第一版不自动把普通聊天消息里的图片转换成预设条目图片；两者是不同能力。
- 第一版不替换 PromptManager 的完整导入/导出格式；只保证完整 Chat Completion 预设 JSON。
- 第一版不承诺 PromptManager 的“导出全部用户提示词 / 导入提示词”也能携带图片。该路径导出的是 `{version,type,data:{prompts,prompt_order}}`，没有 `extensions`，需要后续单独扩展。

参考文档：

### 2.2 Chat Completion Preset JSON 结构

本仓库导出的预设样例：`Plugin/Plugin_Preset_Images/sample/空预设.json`。

关键顶层字段：

```json
{
    "name": "空预设",
    "prompts": [ ... ],
    "prompt_order": [ ... ],
    "extensions": {},
    "media_inlining": false,
    "inline_image_quality": "low",
    "request_images": false
}
```

`prompts` 是提示词定义列表。样例共 16 条，包含系统提示词、marker 和用户自定义提示词。典型形态：

```json
{
    "content": "提示词内容",
    "identifier": "ee1b96db-a073-4849-863b-a18cb185f854",
    "name": "预填充",
    "role": "assistant",
    "system_prompt": false,
    "injection_depth": 4,
    "injection_order": 100,
    "injection_position": 0,
    "injection_trigger": [],
    "marker": false
}
```

`prompt_order` 是按角色/群组维护的提示词启用状态和顺序：

```json
{
    "character_id": 100000,
    "order": [
        { "enabled": true, "identifier": "main" },
        { "enabled": true, "identifier": "chatHistory" }
    ]
}
```

重要结论：

- 图片不应只按 `prompts` 数组下标保存，因为不同角色的 `prompt_order` 不同，顺序也会变化。
- 应使用稳定的 `identifier` 关联图片。identifier 也是 PromptManager 查找、排序、导入合并的主键。
- 样例顶层已经有 `extensions: {}`，为插件数据提供了标准落点。

### 2.3 预设保存、导入、导出链路

前端：

- `src/scripts/openai.js`
  - `settingsToUpdate` 明确包含 `extensions`、`prompts`、`prompt_order`。
  - `getChatCompletionPreset(settings)` 会从当前 settings 复制预设字段。
  - `saveOpenAIPreset(name, settings, triggerUi)` 通过 `/api/presets/save` 保存。
  - `onPresetImportFileChange(e)` 解析预设 JSON，并在保存前触发 `OAI_PRESET_IMPORT_READY`。
  - `onExportPresetClick()` 在 JSON 序列化前触发 `OAI_PRESET_EXPORT_READY`。
  - `onSettingsPresetChange()` 应用预设时对 `extensions` 有特殊处理：
    ```js
    if (key === 'extensions') {
        oai_settings.extensions = preset.extensions || {};
        continue;
    }
    ```
    这意味着 `extensions` 中的插件数据会随预设切换自动更新到当前 `oai_settings`。

- `src/scripts/preset-manager.js`
  - `readPresetExtensionField({ name, path })`
  - `writePresetExtensionField({ name, path, value })`
  - 这两个方法专门用于在预设的 `extensions` 中读写扩展字段，可以同时更新当前 settings 和指定预设文件。

后端：

- `src-tauri/crates/tt-application/src/dto/preset_dto.rs`
  - `SavePresetDto.preset` 是 `serde_json::Value`，任意 JSON 对象。
- `src-tauri/crates/tauritavern/src/presentation/commands/preset_commands.rs`
  - `save_preset` 只校验 name 非空、preset 非 null。
  - 没有对 `prompts`、`prompt_order`、`extensions` 做 schema 级校验。
- `src-tauri/crates/tauritavern/src/infrastructure/repositories/file_preset_repository.rs`
  - `data_with_name()` 后直接写 JSON 文件。

因此从“保存/导入不报错”的角度，插件数据放在 `extensions` 或提示词对象的额外字段里，当前后端都能原样保存和返回。需要注意的是：能被保存不等于能生成图片，生成图片还需要前端组装链路配合。

### 2.4 PromptManager 的提示词数据流

核心位置：`src/scripts/PromptManager.js`。

- `sanitizeServiceSettings()`：
  - 修掉 null；
  - 补默认提示词；
  - 给缺失 identifier 的提示词补 UUID；
  - 不会把提示词对象中的未知字段删掉。
- `getPromptCollection(generationType)`：
  - 按当前角色 `prompt_order` 遍历；
  - 只把 `entry.enabled === true` 的条目加入 collection；
  - 对每个 `prompt` 调用 `preparePrompt(prompt)`。
- `preparePrompt(prompt, original)`：
  - `new Prompt(prompt)`；
  - 对 `content` 做宏替换；
  - `Prompt` 构造函数只复制已知字段，未知字段会在这里被丢弃。
- `Message.fromPromptAsync(prompt, tokenHandler)`：
  - 调用 `Message.createAsync(prompt.role, prompt.content, prompt.identifier, tokenHandler)`；
  - 不处理图片。

这说明：如果插件把图片只放进 `prompts[i].images`，必须经过 `preparePrompt` 包装器把它带到生成的 `Prompt` 对象上，或者通过 `identifier` 在生成时重新查表。

生成组装时，提示词被分为三类，见 `src/scripts/prompt-injections.js`：

```js
export const INJECTION_POSITION = {
    RELATIVE: 0,
    ABSOLUTE: 1,
    ATTACH_EXISTING: 2,
};
```

- Relative：通过 `Message.fromPromptAsync()` 进入 `ChatCompletion`，最容易接入图片。
- Absolute / In-chat：`populationInjectionPrompts()` 只对 `prompt.content` 做字符串 join，再作为纯文本消息插入。
- Attach existing：`applyAttachedPromptsToMessages()` 只做字符串拼接，目标是原始聊天消息。

因此：

- 图片支持对 Relative 条目最自然。
- Absolute 和 Attach 需要在最终组装后做额外处理，或修改 `openai.js`/`prompt-injections.js` 核心逻辑；不建议第一版同时覆盖。
- marker 条目要进一步区分：
  - `main`、`worldInfoBefore`、`worldInfoAfter`、`charDescription`、`charPersonality`、`scenario`、`personaDescription`、`nsfw`、`jailbreak`、`enhanceDefinitions` 等在 `preparePromptsForChatCompletion()` 中可能由合成系统提示词补位，最终仍会经过 `Message.fromPromptAsync()`，可通过 identifier 挂图片。
  - `chatHistory`、`dialogueExamples` 等由专门函数直接创建消息，不经过 `Message.fromPromptAsync()`，不能简单挂图片。

## 3. DeepSeek-V4.1-Flash 相关现状

### 3.1 前端当前配置

- 前端 Chat Completion Source 中有 `deepseek`。
- 模型选择 UI 当前选项位于 `src/index.html`：
  - `deepseek-v4-flash`
  - `deepseek-v4-flash-vision-exp`
  - `deepseek-flash`
  - `deepseek-v4-pro`
  - `deepseek-chat`
  - `deepseek-reasoner`
  - `deepseek-coder`
- 默认模型：`src/scripts/openai.js` 中 `deepseek_model: 'deepseek-flash'`。
- `supportsCustomModels` 对 DeepSeek 为 true，因此理论也可选自定义模型 ID。
- 当前前端未提供 `deepseek-v4.1-flash` 内置项；Rust 测试里出现了 `OR/DeepSeek-v4.1-flash`。

### 3.2 前端视觉能力判断

`src/scripts/openai.js` 中 `isImageInliningSupported(settings)`：

```js
case chat_completion_sources.DEEPSEEK:
    return ['deepseek-v4-flash-vision-exp', 'deepseek-flash'].includes(settings.deepseek_model);
```

也就是说：

- 当前项目内建的“聊天消息图片内联”仅明确认这两个 DeepSeek 模型。
- `DeepSeek-V4.1-Flash` 没有被这个判断覆盖。
- `OPENCODE` 来源默认也不在 `isImageInliningSupported()` 的视觉分支里。
- 如果插件直接向请求注入 `image_url`，不应依赖这个函数判断，否则目标模型会被错误跳过。

### 3.3 Rust payload 现状

Rust 请求构造在 `src-tauri/crates/tt-application/src/services/chat_completion_service/payload/`。

- `mod.rs` 将 `ChatCompletionSource::DeepSeek` 路由到 `deepseek::build`。
- DeepSeek 的 OpenAI-compatible 兼容来源（Custom / OpenCode 的 OpenAI-compatible 格式）也会经过 DeepSeek 参数适配。
- `deepseek.rs` 中：
  - 原生 DeepSeek 会启用/禁用 `thinking`；
  - 处理 `reasoning_effort`；
  - 对 model 的最终路径段做判断：
    ```rust
    last_segment.starts_with("deepseek-v4") || last_segment.starts_with("deepseek-flash")
    ```
    所以 `OR/DeepSeek-v4.1-flash` 会被识别为 DeepSeek V4 系列兼容模型。
- `prompt_post_processing.rs` 的 `normalize_message_content()` 会把 `content` 数组中的：
  - `type = "text"` 转成文本段；
  - `type = "image_url"` / `video_url` / `audio_url` 暂存为 media token，最后再还原成原始媒体部分。
- `openai.rs` 的 `build_chat_completion_payload()` 会整体转发 `messages`，不会无条件丢弃 `image_url`。
- `deepseek.rs` 在调用 `openai::build(payload)` 前执行 `post_process_prompt(... SemiTools ...)`；媒体部分会被保留并重组成数组。

结论：后端已经具备接收和转发 OpenAI-compatible `image_url` 内容部分的基础能力。插件的主要工作在前端 UI、预设持久化和 PromptManager/Message 组装接入。

## 4. 图片数据如何进入最终请求

### 4.1 内建聊天图片的现有机制

普通聊天消息附件图片的现有逻辑在 `src/scripts/openai.js` 的 `populateChatHistory()` 中：

```js
if (imageInlining && media.type === MEDIA_TYPE.IMAGE) {
    await chatMessage.addImage(media.url, settings);
}
```

`Message.addImage()`：

- 如果传入的不是 data URL，会先 fetch；
- 按当前 source 决定是否压缩；
- 追加：
  ```js
  this.content.push({
      type: 'image_url',
      image_url: {
          url: image,
          detail: quality,
      },
  });
  ```
- 估算并累加图片 token。

这说明插件可以复用同一套消息格式。但预设条目图片不是聊天消息附件，需要插件在 `Message` 创建后补挂。

### 4.2 推荐的生成接入点

第一版推荐包装两个内部模块方法：

1. `PromptManager.prototype.preparePrompt`
   - 在保留原逻辑的基础上，根据当前 `PromptManager.serviceSettings.extensions.tauritavern.presetPromptImages` 和 `prepared.identifier`，把图片元数据赋给 `prepared.presetPromptImages`。
   - 通过 `this.serviceSettings` 读取，可以让普通 UI 组装和 Agent/headless 组装都使用“当前正在组装的预设设置”。

2. `Message.fromPromptAsync`
   - 调用原方法创建 `Message`；
   - 如果 `prompt.presetPromptImages` 存在，则把图片追加到 message content；
   - 推荐直接使用 `Message.addImage()`，或按存储的 `detail` 调用等价逻辑；
   - 必须同步更新 message token，否则上下文预算会低估图片成本。

伪代码级流程：

```text
预设 JSON
  -> extensions.tauritavern.presetPromptImages.items[identifier]
  -> PromptManager.preparePrompt 挂到 prepared.presetPromptImages
  -> Message.fromPromptAsync 创建 Message 后追加 image_url
  -> ChatCompletion.getChat() 输出 content 数组
  -> /api/backends/chat-completions/generate
  -> Rust payload builder 保留 image_url
  -> DeepSeek / OpenCode / OpenRouter / Custom 上游
```

### 4.3 为什么不用 `CHAT_COMPLETION_PROMPT_READY` 作为主接入点

- 该事件在 `prepareOpenAIMessages()` 中发射，事件数据是 `{ chat, dryRun }`。
- `chat` 是 `ChatCompletion.getChat()` 之后的普通 `{ role, content }` 数组，已经丢失了 `Message.identifier`。
- 没有 identifier 就只能按文本内容、顺序或 marker 猜测对应关系，不可靠。
- `docs/Agent/PromptAssembly.md` 明确说明：
  > 依赖普通 `CHAT_COMPLETION_PROMPT_READY` 事件改写提示词的扩展不会参与这条独立组装路径。
- 因此它不适合作为唯一 seam。

`GENERATE_AFTER_DATA` 可作为最终 request 级别的兜底，但同样缺少 identifier 映射，建议只作为后续支持 Absolute/Attach 时的降级方案。

## 5. 预设 JSON 中的图片存储方案

### 5.1 方案 A：把图片放在每个 prompt 条目里

示例：

```json
{
    "identifier": "ee1b96db-a073-4849-863b-a18cb185f854",
    "name": "预填充",
    "content": "文本提示词",
    "images": [
        {
            "dataUrl": "data:image/jpeg;base64,...",
            "detail": "auto"
        }
    ]
}
```

优点：

- 语义上最贴近“给提示词条目添加图片”。
- 随 `prompts` 数组走，PromptManager 的完整提示词导入/导出路径也可能保留。
- 当前 `PromptManager` 不校验未知字段，插件缺失时大概率被忽略。

风险：

- 修改了标准提示词条目的形状；未来上游如果增加严格 schema 校验，风险比独立扩展字段高。
- `Prompt` 构造函数只复制已知字段，`preparePrompt` 仍需额外搬运。
- 某些导入/合并逻辑若重建 prompt 对象，可能丢失图片。

### 5.2 方案 B：放在 `extensions.tauritavern.presetPromptImages`（推荐）

示例：

```json
{
    "extensions": {
        "tauritavern": {
            "presetPromptImages": {
                "version": 1,
                "items": {
                    "ee1b96db-a073-4849-863b-a18cb185f854": [
                        {
                            "id": "img-uuid",
                            "name": "reference.jpg",
                            "mime": "image/jpeg",
                            "dataUrl": "data:image/jpeg;base64,...",
                            "detail": "auto",
                            "width": 1024,
                            "height": 768,
                            "bytes": 182000
                        }
                    ]
                }
            }
        }
    }
}
```

优点：

- 不改变 `prompts[]` 条目的标准结构。
- 符合现有项目约定：项目已经在 `extensions.tauritavern.omit_params` 中存放扩展状态。
- `settingsToUpdate` 已包含 `extensions`；`onSettingsPresetChange()` 已特殊处理 `extensions`。
- `preset-manager.js` 提供 `readPresetExtensionField()` / `writePresetExtensionField()` 专门读写。
- 插件缺失时，SillyTavern 只会把它当未知 extension 字段，不影响文本提示词。

代价：

- 需要按 identifier 维护映射；删除提示词时可能留下孤儿数据，需要清理策略。
- PromptManager 的独立“导入/导出提示词”路径不会带上 `extensions`，第一版需要明确不覆盖该路径。

### 5.3 推荐的数据字段

建议支持：

- `dataUrl`：必须为 data URL，保证预设自包含、离线可迁移。
- `detail`：`auto` / `low` / `high`，最终映射到 `image_url.detail`。
- `name` / `mime` / `width` / `height` / `bytes` / `id`：用于 UI 和校验，非生成必需。
- `version`：存储 schema 版本，便于未来迁移。

不建议：

- 存远程 URL 作为主格式：预设不完整、离线不可用，还会引入网络请求与 CORS/隐私问题。
- 把二进制以非 data URL 的裸 base64 存进 JSON 后不记录 MIME：难以校验和渲染。

### 5.4 兼容性判断

当前代码的兼容性证据：

- OAI 预设导入：`onPresetImportFileChange()` 只做 `JSON.parse` 和敏感字段检查，不做提示词 schema 校验。
- 后端 `save_preset`：`preset` 为任意 `serde_json::Value`，只拒绝 null。
- PromptManager：
  - `isPromptManagerImportDataValid()` 只要求 `data.prompts` 数组且每个元素有 identifier；
  - `sanitizeServiceSettings()` 会保留提示词未知字段；
  - 不会因为 `extensions` 中存在未知嵌套对象而报错。
- `onSettingsPresetChange()` 会无条件接受 `extensions` 对象。

因此方案 B 最符合“没有插件也能正常导入并文本工作”的要求。方案 A 在当前仓库也可工作，但建议作为备选。

## 6. 图片大小、压缩与性能约束

Base64 会让图片体积膨胀约 33%，再叠加 JSON pretty print（`JSON.stringify(preset, null, 4)`）和前后端结构化克隆，预设会迅速变大。

建议第一版就设置硬限制：

- 允许 MIME：`image/jpeg`、`image/png`、`image/webp`（可考虑转成 JPEG/WebP）。
- 单张建议不超过 1.5 MiB base64 文本，具体数值待对齐。
- 单个提示词建议不超过 4 张图片。
- 单个预设总图片数据建议不超过 16 MiB base64 文本。
- 入库前用 Canvas 做缩放到最大边约 2048px，并重新编码以顺手清理 EXIF 元数据。
- UI 显示总大小和单条图片大小，超限时 fail fast，不静默保存。
- 预设导入时如果已有插件数据超限，建议提示用户并允许清除，而不是直接让生成崩溃。

注意：

- `Message.compressImage()` 在当前实现中只对部分 source 强制压缩；DeepSeek 原生不一定走压缩分支。
- 生成时再压缩不能减少预设 JSON 体积，所以应在“添加图片到预设”时压缩。

## 7. 生成接入的细节风险

### 7.1 system 消息与 `squash_system_messages`

`ChatCompletion.squashSystemMessages()` 当前用字符串拼接合并连续的 system 消息：

```js
lastMessage.content += '\n' + message.content;
```

如果 system 消息的 `content` 已经是图片数组，这会产生 `[object Object]` 或被强制转成字符串，破坏多模态内容。

处理建议：

- 包装 `ChatCompletion.prototype.squashSystemMessages`，让含非字符串/含 media 的 system 消息不参与字符串拼接；或
- 实现多模态安全合并；或
- 第一版限制图片只挂在非 system 角色，但这会排除 Main/Nsfw/Jailbreak 等常见系统提示词，需要用户确认是否接受。

建议不要让插件在 `squash_system_messages = true` 时静默生成损坏请求。

### 7.2 Absolute / Attach 条目

- Absolute 条目由 `populationInjectionPrompts()` 处理，只 join `prompt.content` 字符串。
- Attach 条目由 `applyAttachedPromptsToMessages()` 处理，只拼接目标消息字符串。
- 这两处都没有 identifier 级图片通道。
- 第一版建议只支持 `injection_position = 0`（Relative）的条目，并在 UI 上明确提示；后续再评估 core seam 或事件级兜底。

### 7.3 marker 条目

- `chatHistory`、`dialogueExamples` 不经过 `Message.fromPromptAsync()`，不适合作为第一版图片挂载对象。
- `main`、`jailbreak`、`nsfw` 等 marker 在 `preparePromptsForChatCompletion()` 中会被合成文本提示词，最终可能可以挂载，但需要逐个验证 role/squash/override 行为。
- 建议第一版只对“非 marker 且 Relative”的条目开放 UI；或提供明确的允许列表。

### 7.4 token 预算

- 直接用数组替换 message content 后，必须同步图片 token 成本。
- 复用 `Message.addImage()` 最省事；如果自行追加 `image_url`，应调用或复刻 `Message.getImageTokenCost()` 的逻辑。
- `ChatCompletion.add()` 会在消息加入时检查 token 预算；图片 token 必须在检查前完成累加。

### 7.5 模型能力判断

插件需要自己的视觉能力矩阵，不能用 `isImageInliningSupported()` 原样判断 DeepSeek V4.1 Flash：

- 原生 DeepSeek：当前函数只认两个模型。
- OpenCode：当前函数默认没有 OPENCODE 分支。
- OpenRouter：可以利用模型列表的 `architecture.input_modalities.includes('image')`。
- Custom：当前函数直接返回 true，但最终取决于用户配置的 endpoint/model。

建议插件至少提供：

- 配置/模型能力 allowlist；
- 当前 source + model 不匹配时给出明确提示；
- 用户可以选择“仍要发送”，但默认 fail fast 或明确警告。

### 7.6 内部 seam 的稳定性风险

推荐方案会包装 `PromptManager.prototype.preparePrompt`、`Message.fromPromptAsync`，必要时还包括 `ChatCompletion.prototype.squashSystemMessages`。

这些对象虽然由 `src/scripts/openai.js` / `src/scripts/PromptManager.js` 导出，但它们不是 `docs/FrontendHostContract.md` 中承诺的第三方 Public Contract，更接近上游模块内部 ABI。

取舍：

- 好处：能拿到 prompt identifier，支持普通 UI 组装和 Agent headless 组装，语义比事件注入可靠。
- 风险：上游重构 `PromptManager` 或 `Message` 后，插件可能失效。
- 缓解：
  - 插件启动时检测目标方法是否存在，缺失时明确报错或禁用图片；
  - 把包装器集中在单独模块，减少对业务逻辑的侵入；
  - 长期如果该能力被更多模型/预设使用，应评估把“提示词条目媒体”做成上游/core 能力。

### 8.1 存储

- 使用 `extensions.tauritavern.presetPromptImages`。
- schema 带 `version`，当前为 `1`。
- key 为 prompt `identifier`，值为图片数组。
- 图片统一存 data URL。
- 增删改通过 `getPresetManager('openai').writePresetExtensionField({ path: 'tauritavern.presetPromptImages', value })` 持久化。

- 在 PromptManager 列表条目或编辑弹窗中增加图片管理入口。

### 8.3 生成

- 包装 `PromptManager.prototype.preparePrompt`，按 identifier 从 `serviceSettings.extensions` 取出图片元数据并挂到 prepared prompt 上。

- 包装或规避 `ChatCompletion.squashSystemMessages` 的数组拼接问题。
- 不依赖 `CHAT_COMPLETION_PROMPT_READY` 作为主接入；这样 Agent/headless 的 PromptManager 组装路径也有机会生效。

- `OAI_PRESET_CHANGED_AFTER`：刷新 UI 绑定。

### 8.5 兼容策略

- 插件数据只放在 `extensions` 命名空间，不要求 `prompts[]` 增加字段。
- 预设中没有插件字段时，插件不改变任何生成行为。
- 模型不支持图片时，不静默丢弃；根据用户策略明确是“跳过并警告”还是“阻止生成”。
- 插件卸载后，预设仍以纯文本工作。

## 11. 已对齐决策（2026-09-30）

本轮讨论后，以下内容作为当前开发基线：

1. **DeepSeek-V4.1-Flash 不是插件的特判对象**  
   官方原生多模态模型可能会被路由到 `deepseek-flash`；选择它是为了跑通插件链路。具体上游模型是否支持图片、上游协议是 OpenAI 还是 Claude 等，由预设开发者负责。插件只提供“给提示词条目挂图片并发送”的功能。

2. **实际 model ID 不由插件决定**  
   插件不硬编码 `deepseek-v4.1-flash`、`deepseek-v4-flash` 或其他模型 ID，也不替用户选择来源。model ID 由预设使用者自己配置。

3. **图片角色由预设开发者决定**  
   插件只提供 role 选项/能力，不判断某模型是否接受 system、user、assistant 消息中的图片。

4. **图片存储在 `extensions.tauritavern.presetPromptImages`**  
   使用方案 B。图片按 prompt `identifier` 关联，不把图片字段塞进标准 `prompts[]` 条目。

5. **不设默认硬限制，但提供可配置限制和警告**  
   插件设置中提供大小、数量等限制配置；默认允许继续，但在添加、导入、导出等环节给出明确警告和体积展示。

6. **复用提示词条目的 enabled 开关**  
   已经禁用的提示词条目不发送图片；插件设置中另有一个总开关，总开关关闭后不再发送任何图片。

7. **导入预设时给出警告和选择**  
   导入带图片数据的预设时，插件提示用户，并让用户决定是否启用插件/保留/清理这些图片。

8. **优先实现多模态安全的 `squash_system_messages` 合并**  
   不能沿用当前简单的字符串 `+=` 合并，需要保证 system 消息中的 `text` / `image_url` 内容部分不损坏。

9. **marker 条目禁止挂图片，只支持 Relative 条目**  
   `marker: true` 的提示词条目不提供图片入口，也不会发送图片。  
   只支持 `injection_position = 0`（Relative）的提示词条目。

10. **图片数据放在 `extensions.tauritavern.presetPromptImages` 更稳定**  
    不与标准 `prompts[]` 结构耦合，缺失插件时可被当作未知扩展字段忽略。

11. **插件不提供转码功能**  
    不提供裁剪、缩放、格式转换等图片编辑能力；图片格式/大小/兼容性由预设开发者自己处理。

12. **插件图片需要在 Agent/headless 组装路径中生效**  
    不能只依赖 `CHAT_COMPLETION_PROMPT_READY`；需要覆盖 PromptManager 的 headless 组装路径。

13. **UI 交互支持拖拽和粘贴，不需要裁剪**  
    可由拖拽、粘贴或文件选择入口添加图片；不提供裁剪 UI。

14. **JSON 体积不是首要阻塞问题**  
    不因为 JSON 变大而牺牲功能；但仍应提供体积提示和可选限制警告。

## 12. 仍需注意的方面（新增）

### 12.1 “插件启用”的语义需要明确

这里至少有三个不同层级：

- SillyTavern 扩展本身是否启用；
- 插件设置中的总开关；
- 预设导入时用户选择的“是否处理这些图片”。

如果扩展本身被禁用，标准扩展加载机制通常不会执行插件 JS，此时插件无法在导入预设时给警告。也就是说：

- 插件已安装且已启用、但总开关关闭：可以警告并询问用户是否打开总开关。
- 插件已安装但扩展被禁用：插件 JS 不运行，无法警告。
- 插件未安装：更无法警告，只能保证预设仍按文本工作。

需要明确：导入警告是“询问是否打开插件总开关”，还是“是否清除预设里的图片数据”，还是“给当前预设写一个 `enabled=false` 标记”。建议至少区分：

- 插件级总开关：设备/插件设置，不属于预设。
- 预设图片数据是否保留：属于预设数据，默认保留。
- 生成时是否发送：由“扩展已启用 + 插件总开关开 + 条目 enabled + 条目 Relative + 非 marker”共同决定。

### 12.2 PromptManager 独立导入/导出与图片映射的一致性

完整 Chat Completion 预设 JSON 包含 `extensions`，所以方案 B 能随完整预设流转。但是 PromptManager 自己的：

- `handleFullExport()`
- `handleCharacterExport()`
- `handleImport()`

只处理：

```json
{
    "version": 1,
    "type": "full",
    "data": {
        "prompts": [],
        "prompt_order": []
    }
}
```

不包含 `extensions`。因此：

- 图片不会跟随 PromptManager 的提示词导入/导出。
- 如果用户用 PromptManager 导入一组 prompt，identifier 可能覆盖/合并现有条目，但 `presetPromptImages` 不会同步变化，可能产生：
  - 旧图片挂到同 identifier 的新提示词上；
  - 已有提示词失去了对应图片；
  - 孤立图片映射。

需要决定第一版是否：

- 明确限定“只保证完整预设 JSON”；
- 或者也包装 `PromptManager.prototype.import/export`，做图片映射合并与提示。

### 12.3 提示词类型变化后的图片处理

当前已决定只支持：

- `marker !== true`
- `injection_position` 为 Relative（缺省视为 Relative）

但用户可以在编辑表单中把提示词从 Relative 改成 In-chat / Attach，也可能导入带图片但 position/marker 不合法的预设。需要定义：

- 已有图片的条目改成非法 position 时：
  - 保留图片但不发送，并警告；
  - 阻止保存修改；
  - 自动迁移为合法 position。
- 导入预设时发现图片挂在 marker / Absolute / Attach 上：
  - 保留数据但标记为“不可发送”；
  - 提示用户删除；
  - 直接剥离。
- 是否允许图片挂在 `enabled=false` 的条目上：建议允许保留，编辑期可见，生成时不发送。

### 12.4 system 消息安全合并的语义

“多模态安全合并”需要再定义具体行为：

- 合并后内容部分的顺序是否必须保持原顺序；
- 相邻 `text` 段是否合并成一个 text part；
- 遇到 `image_url` / 其他 media part 时是否停止合并；
- 合并后的 token 如何重新计算；
- 如果 media part 无法解析，是跳过、保留还是报错。

建议约定：

- 保持 part 原始顺序：`text(A)` + `image(X)` + `text(B)` 不应变成 `text(A+B)` + `image(X)`，除非明确接受这种语义。
- 只合并相邻的纯文本 part，媒体 part 作为边界。
- 合并 token 至少不能低估；如果 `Message.getImageTokenCost()` 可用，按图片单独累加，文本按原消息或重新计数。
- `excludeList` 和现有 `squashSystemMessages` 的排除语义保持不变。

### 12.5 不转码与现有 `Message.addImage()` 的自动压缩可能冲突

当前 `Message.addImage()` 自身会在某些 source 下压缩、重编码或转换不支持的 MIME。用户已决定“不提供转码功能”，因此需要明确：

- 插件是否完全保留用户原始图片字节，只追加 `image_url`；
- 还是复用 `Message.addImage()`，接受其中已有的自动压缩/格式转换行为。

如果要求严格不转码：

- 应实现插件自己的 append 逻辑，不调用 `Message.addImage()`；
- 仍需要图片 token 估算，可调用 `Message.getImageTokenCost()`；
- 对无法识别的图片格式给出警告，但仍按 data URL 原样发送或由预设开发者承担后果。

如果允许复用 `Message.addImage()`：

- 实现更简单；
- 但“无转码”承诺需要改为“插件不主动提供转码 UI，生成链路可能进行已有压缩”。

### 12.6 图片顺序与空文本消息

需要定义：

- 图片在文本之前还是之后；
- 同一提示词多张图片的顺序是否可由用户调整；
- 是否支持每条图片单独设置 `before` / `after`；
- 当提示词内容为空时，最终 content 是：
  - `[{ type: 'image_url', ... }]`
  - 还是 `[{ type: 'text', text: '' }, { type: 'image_url', ... }]`

`Message.addImage()` 会为空的字符串内容生成空 text part；某些上游可能不接受空 text part。建议插件自行控制：内容为空时只输出图片 part，或明确警告。

### 12.7 持久化写入的时序与竞争

图片增删改可能触发多次保存，必须防止：

- 用户刚添加图片立刻切换预设，导致写丢失；
- 用户导出时读到旧数据；
- 多个异步 `writePresetExtensionField()` 并发覆盖；
- 预设已切换，但 debounce 的保存还指向旧预设。

建议：

- 统一一个串行保存队列；
- 在 `OAI_PRESET_CHANGED_BEFORE`、`OAI_PRESET_EXPORT_READY`、`beforeunload` 前 flush；
- 保存时捕获当前 preset name，而不是稍后再取 `getSelectedPresetName()`；
- 写失败时给出明确错误，不静默吞掉。

### 12.8 Agent/headless 路径中的总开关

Agent/headless 使用独立的 PromptManager，但其 `serviceSettings` 来自被引用的预设，因此 `extensions.tauritavern.presetPromptImages` 可以被带入。

需要确保：

- 插件总开关来自当前设备/插件设置，而不是来自预设的 `extensions`；
- 被 Agent 引用的预设即使不是当前 UI 选中的预设，其图片仍按该预设的 identifier 映射生效；
- 如果总开关关闭，Agent 引用该预设时也不能发送图片；
- 如果 headless 组装发生在 UI 未加载/插件未激活时，需要明确是否支持；常规情况下应等 `APP_READY` 后再执行 Agent 运行。

### 12.9 限制与警告的默认值

用户已同意“不设硬限制 + 提供配置 + 给警告”。仍需决定：

- 默认警告阈值是多少；
- 是否允许设置为 0 表示无限；
- 超限时是仅 toast 警告，还是弹窗让用户确认；
- 导入预设时是否自动统计并显示 `presetPromptImages` 的总大小；
- 是否显示当前预设图片体积到插件设置 UI。

### 12.10 移动端 fallback

桌面端可以拖拽，但不是所有移动端 WebView 都支持 HTML5 drag/drop。建议：

- 拖拽/粘贴/文件选择三种入口都提供；
- 移动端至少保留 `input[type=file]`；
- 粘贴事件只接受 `image/*` 类型。

### 12.11 schema 版本、未知字段与数据修复

建议 `presetPromptImages` 增加：

```json
{
    "version": 1,
    "items": {}
}
```

需要定义：

- 遇到更高 version 时：保留数据、警告、不处理；
- 遇到非法结构时：保留文本预设可用，但禁用图片处理并提示；
- 遇到孤立 identifier（prompt 已不存在）时：保留、提示或清理；
- 遇到重复/缺失 identifier 时：不覆盖其他提示词，明确警告。

### 12.12 隐私警告

用户已决定不转码。原始图片可能保留 EXIF、GPS、设备信息等敏感元数据。建议至少在添加/导入/导出时提示：

- 图片会以原始 data URL 嵌入预设 JSON；
- 分享预设等于分享图片及其可能存在的元数据；
- 如需清理元数据，由预设开发者自行处理。

### 12.13 建议的回归清单

实现后至少覆盖：

- 没有插件时导入含 `presetPromptImages` 的预设，文本功能正常；
- 插件总开关关闭时，文本功能正常且不发送图片；
- 条目 `enabled=false` 时不发送图片；
- marker 条目和 Absolute / Attach 条目不发送图片；
- Relative 自定义条目能发送 `image_url`；
- 空提示词 + 图片的最终 content 形态符合约定；
- system 消息含图片且 `squash_system_messages=true` 时不损坏；
- 多张图片的顺序稳定；
- 预设导出/导入后图片数据不丢；
- 预设切换、导出、页面关闭前写入已 flush；
- Agent/headless 引用预设时图片生效且受总开关控制；
- 非法/超限图片有明确警告，不静默产生损坏请求。

## 13. 补充对齐决策与实现方向（2026-09-30）

本轮补充确认：

1. **提示词类型变更后的图片处理**
   - 保留图片数据，但不发送。
   - 在 UI 和导入/加载时给出警告。
   - 判定条件保持：
     - `marker === true` 不发送；
     - `injection_position !== 0` 不发送。

2. **只保证完整预设 JSON 的图片流转**
   - PromptManager 的 `import/export` 不承载 `extensions.tauritavern.presetPromptImages`。
   - 在插件 JS 已加载的前提下，对 PromptManager 的 import/export 给出警告。
   - 内部维护一份“当前哪些 identifier 带有图片”的记录，用于在 import/export 时提示冲突或丢失风险。
   - 完整 Chat Completion 预设 JSON 的导入/导出继续作为图片数据的主通道。

3. **导入时“是否启用插件”的准确语义**
   - 扩展本身已经启用。
   - 导入的预设带有图片数据。
   - 插件内部总开关当前处于关闭状态。
   - 此时提示用户是否打开插件内部总开关；图片数据保留在预设中。
   - 如果扩展本身未启用或未安装，插件 JS 不会运行，因此无法拦截导入过程。

4. **不提供 UI 转码**
   - 插件不提供裁剪、缩放、格式转换 UI。
   - 接受生成链路中现有 `Message.addImage()` 的自动压缩/重编码行为。
   - 实现时优先保证：
     - 图片以 data URL 嵌入预设；
     - 支持按存储的 `detail` 发送；
     - 图片格式/上游兼容性由预设开发者负责。

5. **图片顺序**
   - 避免空 text part；提示词内容为空时，只发送图片 part。
   - 每条图片支持：
     - `before`：文本之前；
     - `after`：文本之后。
   - 保持同一提示词内图片配置顺序稳定。

6. **TypeScript 实现**
   - 插件源码使用 TypeScript，编译输出到 `dist/`。
   - 运行时入口为 `dist/index.js`。
   - 目的：把存储、设置、DOM 编辑器、运行时 hooks、preset 事件和 multimodal 合并分开维护。

## 14. 新增项目内 API 参考

插件目录下新增了项目内参考文档：

- `Plugin/Plugin_Preset_Images/docs/api指南-图像理解.md`

其中与插件直接相关的 DeepSeek Flash 事实：

- `deepseek-flash` 支持图片输入；旧模型名 `deepseek-v4-flash-vision-exp` 的请求会由最新 Flash 模型承接。
- 图片使用标准 OpenAI-compatible `content` block 数组。
- 内联图片使用 `{ "type": "image_url", "image_url": { "url": "data:...base64..." } }`。
- `image_url.detail` 可用值包括：
  - `low`
  - `high`
  - `original`
  - `auto`
- 文档说明图片格式由实际内容判断，支持 JPEG / PNG / GIF / WebP。
- 内联 base64 会计入 48 MiB 请求体限制。

因此插件当前 schema 已支持 `detail: auto | low | high | original`。插件不内建 48 MiB 硬限制，继续通过可配置警告阈值提醒用户。

## 15. v2 排序模型与多语言实现记录（2026-09-30）

后续改进已按以下方案实现：

### 15.1 数据模型 v2

图片布局为：

```json
{
  "version": 2,
  "items": {
    "<prompt-id>": {
      "before": [ ...images ],
      "after": [ ...images ]
    }
  }
}
```

- `before`：提示词文本之前的图片顺序。
- `after`：提示词文本之后的图片顺序。
- 当前只支持 v2；不再保留 v1 迁移逻辑。
- 生成时按 `before + text + after` 的顺序组装多模态 `content`。
- 文本为空时不生成空 `text` part。

### 15.2 UI

- 编辑弹窗中显示“图片块 + Prompt Text 锚点 + 图片块”的排序列表。
- 图片块右侧有与缩略图高度接近的拖动区域，用于拖动排序。
- 图片可跨过 Prompt Text 锚点，在 `before` / `after` 之间移动。
- 新添加或粘贴的图片默认插入 `after` 尾部。
- 每张图片支持单文件替换、删除和 `detail: auto / low / high / original`。
- 位置下拉框默认隐藏，可在插件设置中打开。
- 上移/下移按钮默认隐藏，可在插件设置中打开，作为移动端和键盘 fallback。

### 15.3 多语言

- 支持 `en`、`zh-cn`、`zh-tw`、`ja-jp`。
- 通过扩展 manifest 的 `i18n` 字段接入酒馆原生语言切换。
- UI 文案、toast、错误提示和设置面板都从 locale 文件读取。

## 16. 后续设置与生命周期迭代记录（2026-09-30）

本轮新增决策：

- Global Prompt 类型图片禁用：
  - eligibility 规则为：先要求 `marker !== true && injection_position === 0`；再禁用 `system_prompt === true && forbid_overrides !== true` 的 Global Prompt。
  - 不限制 message `role`。
  - Global Prompt 条目上已有图片不迁移、不特殊清理，但不发送。
- 插件配置存储可选：
  - 默认仍在 `extension_settings.Plugin_Preset_Images`。
  - 可选启用 TauriTavern extension store。
  - 切换存储时弹确认；切到 store 后精确删除 `extension_settings.Plugin_Preset_Images`；切回时保留 store 中的副本。
  - API 不可用时该选项直接禁用。
- 无操作定时器：
  - 只在窗口可见且聚焦时计时。
  - 生成中、编辑弹窗打开、输入框焦点等情况下暂停。
  - 触发前显示倒计时弹窗，可取消。
  - 每次应用启动最多触发一次，重新启用扩展视为同一次启动。
  - 触发后禁用扩展自身；失败时 fallback 到关闭插件功能。
- 卸载：
  - 做成高级设置中的手动按钮，需要二次确认。
  - 卸载时清理 `extension_settings.Plugin_Preset_Images` 精确 key。
  - 卸载时清理 TauriTavern extension store 的 `Plugin_Preset_Images` namespace。
  - 保留 `extensions.tauritavern.presetPromptImages` 预设图片数据。
- 总开关关闭时可选隐藏相关 UI：
  - 只隐藏 PromptManager 图片编辑器。
  - 插件设置面板保持可见，便于重新启用。
